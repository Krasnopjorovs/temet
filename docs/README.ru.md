# Temet nosce — натальная карта, прогноз и совместимость без LLM в рантайме

Клиент вводит дату, время и место рождения → сервис считает карту (Swiss Ephemeris),
собирает отчёт по модулям и ищет совпадения в сети. Ноль GPU и ноль токенов на запрос:
LLM используется только офлайн, чтобы написать тексты к фактам, и каждый текст
попадает в выдачу только после ручного одобрения.

## Главный принцип: доктрина — это данные

Всё астрологическое знание (тела, управители, достоинства, орбисы, веса синастрии,
режимы поиска, составные правила, шаблоны заголовков) лежит в
`doctrine/classic_modern_v1.yaml` → таблицах Postgres. В Python нет ни одной
астрологической константы. Другая школа = другой YAML, можно держать две
доктрины рядом и сравнивать.

## Математика синастрии

Направленная полезность «A получает от B»:

    U(A←B) = Σ_{i∈A, j∈B} Σ_aspects W[i,j,a]·K_a(θ_i − θ_j)  +  Σ_j Σ_h V[j,h]·1[θ_j ∈ дом_h(A)]

Ядро аспекта K_a — чётная периодическая функция; её ряд Фурье
K_a(Δ) = c₀ + Σ cₙ cos nΔ и тождество cos n(α−β) = cos nα cos nβ + sin nα sin nβ
делают всё выражение билинейным: **U(A←B) = q_A · x_B**.

- `x_B` — что человек «излучает»: [1, cos nθ, sin nθ] по 16 телам, n ≤ 48 (D = 1552).
- `q_A` — что человеку «нужно»: доктрина W, V, свёрнутая с его картой, включая дома.
- Неточность времени ±Δt входит точно: для θ ~ U[θ₀−w, θ₀+w] E[e^{inθ}] = sinc(nw)·e^{inθ₀}.
  Неизвестное время = ожидание по суткам, а не «полдень».

Поэтому pgvector (max inner product, HNSW) ищет ровно ту величину, по которой потом
ранжируем. Поиск идёт в обе стороны (индекс по x: кто даёт мне; индекс по q: кому
даю я), итог — произведение Нэша по перцентилям со штрафом асимметрии.

Перцентили — против нулевой модели: `scripts.calibrate` считает распределение скоров
по всем парам популяции (3000 карт → 9 млн пар на ключ). «97» = выше 97% случайных пар.

## Что измерено (Postgres 16 + pgvector, 3000 профилей)

| Проверка | Результат |
|---|---|
| q·x против прямого перебора пар (то же ядро) | расхождение 6·10⁻¹⁵ |
| против точной модели (полное ядро + размытые куспиды) | корреляция > 0.9995 |
| неопределённость времени: формула sinc против Монте-Карло | совпадает в пределах шума |
| выдача API (HNSW в обе стороны) против точного перебора базы | recall@20 = 1.00 во всех режимах |
| карта + отчёт | ~11 мс |
| подбор пар (топ-20, объяснения для топ-5) | ~170 мс |
| калибровка | ~25 с |

`pytest tests/` — 23 теста, включая регрессию: Swiss Ephemeris хранит путь к файлам
по потокам, и без инициализации на каждый поток веб-сервер молча уходил в Moshier
(и терял Хирона). Здесь это ошибка, а не тихая деградация.

## Запуск

    echo "POSTGRES_PASSWORD=$(openssl rand -hex 16)" > .env
    docker compose up -d db
    docker compose run --rm api python -m scripts.bootstrap --geonames
    docker compose up -d api           # http://127.0.0.1:8095 (только loopback)

API: `POST /api/chart`, `POST /api/profiles`, `GET /api/profiles/{handle}/matches?mode=ROMANCE`,
`POST /api/synastry`, `GET /api/places?q=`, `GET /api/doctrine`, Swagger на `/docs`.

Прогноз (`astro/forecast.py`, `POST /api/forecast`, период `week` или `month`, `start`, `tz_now`): транзиты к
натальным точкам с датами входа, точных касаний и выхода (попятные петли — один эпизод, разворот планеты на точке
усиливает тему, «обещание карты» — те же две планеты связаны аспектом и в натале, тип называется), транзиты по домам, Луна по
домам (неделя), новолуния, полнолуния и затмения с натальными точками рядом, попятные Меркурий, Венера и Марс,
прогрессивная Луна. Тема, которую задевают ≥ 2 техники, подтверждена. Погрешность даты от неточного времени
рождения = неопределённость натальной точки / скорость планеты. Насыщенность окна — перцентиль среди случайных
карт и дат (`scripts.forecast_calibrate` → `doctrine/stats/<код>.forecast.json`). Тексты — по ключам `tr:`, `trh:`,
`moon:`, `lun:`, `ecl:`, `retro:`, `pm:`, `pmh:`, `pms:` (564 ключа); параметры — `params.forecast` в доктрине.
Даты проверяются в `scripts.verify_engine` (раздел G): теории Миуса, алгоритм фаз Луны, каталог затмений NASA.

Страница (`app/static`): ночное небо рисует `sky.js` (туманность и звёзды на двух слоях, которые плавно сменяют
друг друга). После расчёта карты небо окрашивается ею: облака цветов знаков тел из `ui_palette.anchors`
(Солнце, Луна, Асцендент), само небо и панели слегка окрашены цветом знака Солнца (`tint`), акцент страницы —
по `accent_from` (знак Солнца или ведущая планета); ведущая планета — ещё одно небольшое облако. Все цвета — в
доктрине (`ui_palette`: у каждого знака два тона, у планет — свой цвет; отдаются в `/api/doctrine`); после их правки
нужен `load_doctrine`. Шрифты Unbounded и Literata (SIL OFL) лежат в `app/static/fonts`: страница не обращается
к сторонним серверам.

Языки (`astro/i18n.py`, `app/static/i18n.js`): русский и английский. Код не знает слов ни одного языка: подписи
астрологии — в доктрине (`label: {ru: …, en: …}` у тел, знаков, домов, аспектов, модулей, режимов, осей синтеза),
строки, которые собирает сервер, — в `params.strings.<язык>`, заголовки прогноза — в `params.forecast.templates.<язык>`
(`{h_ord}` — порядковое число: 1st, 2nd…), слова страницы — в `app/i18n/<язык>.json`. У каждой страницы свой адрес на
каждом языке: `/` и `/about` — русский, `/en/` и `/en/about` — английский; сервер сам подставляет слова, заголовок,
описание, canonical, hreflang, Open Graph и JSON-LD (для поисковиков), отдаёт `/sitemap.xml` и `/robots.txt`. На «/»
посетителя без выбора отправляет на язык браузера, выбор на сайте запоминается (cookie `temet_lang`); старые ссылки
`?lang=en` ведут на адрес языка. API принимает `?locale=`. Страница «Как это работает» — `about.html` и `about.en.html`.
Настройки в `.env`: `PUBLIC_URL` (адрес сайта для canonical и sitemap), `RATE_LIMIT` (запросов к API в минуту с одного
адреса, по умолчанию 120), `DRAFTS_NETS` (сети, из которых видны черновики; через туннель — никогда). Тексты отчёта и прогноза хранятся по языкам (`content.locale`), переводы проходят
`scripts.gate_translation` (сверка с исходником: поля, пункты, длина, имена, запреты, корпус) и собираются
`scripts.build_translation` (служебные поля — из исходника, подписи смысла — по корпусу языка); импорт —
`scripts.import_content <файл> --locale en`, одобрение — `--approve '%' --locale en`. Тест `test_locales_complete…`
проверяет, что у каждой подписи доктрины есть все языки.

Обновление существующей установки:

    docker compose build api
    docker compose exec -T db psql -U astro -d astro < db/002_labels_and_fingerprints.sql
    docker compose exec -T db psql -U astro -d astro < db/003_rule_presents.sql
    docker compose exec -T db psql -U astro -d astro < db/004_content_revisions.sql
    docker compose run --rm api python -m scripts.load_doctrine doctrine/classic_modern_v1.yaml
    docker compose run --rm api python -m scripts.calibrate      # если сменились веса
    docker compose run --rm api python -m scripts.reembed        # если stale_profiles > 0
    docker compose up -d api

`ENABLE_NETWORK=1` в `.env` включает профили и поиск совпадений (по умолчанию выключено: сервис ничего не хранит).
`API_BIND` в `.env` — адрес привязки (по умолчанию 127.0.0.1), `API_PORT` — порт.

## Скрипты

| | |
|---|---|
| `scripts.load_doctrine <yaml>` | доктрина → таблицы + HNSW-индексы нужной размерности |
| `scripts.calibrate [--profiles]` | нулевая модель → квантили (после смены весов — обязательно) |
| `scripts.reembed` | пересчитать карты и векторы после смены доктрины |
| `scripts.synthesis_calibrate content.json` | распределение полюсов осей синтеза по популяции карт |
| `scripts.load_geonames --download` | офлайн-геокодер GeoNames (города > 15k, IANA-зоны) |
| `scripts.seed_synthetic --n 5000` | синтетика для нагрузки (в выдачу людям не попадает) |
| `scripts.export_content_prompts --module karma` | промпт-файлы для недостающих текстов (web UI модели) |
| `scripts.import_content out/*.json` / `--approve 'sign:RAHU:%'` | черновики → одобрение (`--locale en` — английские) |
| `scripts.gate_translation out/*.json --source <исходник>` | проверка переводов против исходных текстов |
| `scripts.build_translation out/*.json --source <исходник> --out <файл>` | переведённый корпус для импорта |
| `scripts.dedupe_scan --content <файл> [--locale en]` | сколько полей прячет снятие повторов на случайных картах |
| `tests.recall_check <handle>` | сверка выдачи API с точным перебором |

Заметность фактов и правил — в одних единицах (масса PageRank тел, на которых они
держатся), поэтому сработавшее правило не всплывает наверх автоматически. Поле
`covers` правила убирает поглощённые им атомарные факты, чтобы отчёт не дублировался.

Калибровка и векторы профилей привязаны к отпечатку доктрины (веса, орбисы, режимы).
Поменяли веса — старая калибровка не применяется молча, `healthz` покажет пустой
`calibrated`, а `/api/doctrine` — число `stale_profiles`. Правка текстов, меток и
правил отпечаток не меняет.

Сборка отчёта для читателя (`astro/report.py`, без LLM, всё в параметрах доктрины): Солнце, Луна и
Асцендент закреплены первыми; в каждом разделе развёрнуты 5 главных положений, остальное — под «ещё»;
положения, общие для поколения, собраны в свёрнутый блок «Фон поколения» с датами из эфемерид;
достоинство планеты — пометка на карточке знака; правило называет свой вариант (тела, знаки, дома);
повторяющиеся пункты и советы скрываются по подписям смысла (`scripts.content_signatures`: общие обороты и нечастые слова, посчитанные по всему корпусу офлайн); управители, стоящие в одном доме, собраны в одну карточку этого дома;
непроверенные каналы не показываются.

Синтез (`astro/synthesis.py`, без LLM): отчёт складывает положения вместе по семи осям из традиции — шесть полярностей знаков и домов (Овен–Весы … Дева–Рыбы) и напряжение огня и земли; оси — параметр доктрины `synthesis_axes`. Каждый текст размечен полюсами, к которым тянет (`axes`), и отчёт считает долю веса карты на каждом полюсе, сравнивая её с популяцией (`scripts.synthesis_calibrate` → `doctrine/stats/<код>.synthesis.json`). Оба полюса сильны — карточка напряжения: в чём конфликт, чего он стоит, как голоса договариваются; один полюс подтверждают несколько положений — сквозная тема (правило свидетельств). Карточка называет положения на каждой стороне, а у них самих стоит пометка оси. После смены разметки текстов калибровку пересчитывают.

Отчёт начинается с блока «Главное в карте»: ведущая пара планет (по PageRank) и
перекосы стихий/крестов, взвешенные важностью планет (пороги — в доктрине).

## Тексты отчёта

Пишет локальная модель офлайн, вы одобряете; на клиента — ноль вызовов LLM.

    python -m scripts.generate_content --url http://localhost:8080 --out content_out \
        --kinds dominant,element,modality --limit 20          # проба: одна партия
    python -m scripts.generate_content --url http://localhost:8080 --out content_out   # всё

Каждая партия сразу пишется в свой файл и в БД как черновик; повторный запуск
продолжает с места остановки; неразборчивый ответ сохраняется в `.err.txt`.
Черновики видны на странице с галочкой «показывать черновики» (или `?drafts=1`),
одобрение — `python -m scripts.import_content --approve 'dominant:%'`.
`?debug=1` показывает ключи и веса фактов.

Готовый корпус можно загрузить и без своей модели — файлом JSON (массив объектов
`{key, title, body, in_life, strength, shadow, action}`):

    python -m scripts.gate_content content.json           # проверка: 0 FAIL
    python -m scripts.gate_content fix.json --context content.json   # перегенерация отдельных полей: объекты
                                                          # {key, action, action_kind} дополняются принятой версией
    python -m scripts.import_content content.json --source claude
    # просмотр: страница с ?drafts=1; одобрение — отдельной командой после просмотра

Каждый автор (своя модель или человек) получает один и тот же промпт
(`doctrine/prompts/content.ru.txt`: роль и принципы) и бриф к ключу (`astro/brief.py`) — посчитанные
факты, а не трактовки: сколько положение держится по эфемеридам и общее ли оно для ровесников,
периоды медленных планет, частота в популяции, все варианты условия составного правила.
Таблицы для брифов считает `python -m scripts.content_stats` (≈30 с) в `doctrine/stats/`.

Каждый совет («Что делать») помечен видом главного действия — `action_kind` из `doctrine/prompts/advice_kinds.ru.json` (виды выделены из самого корпуса; родственные виды объединены в семейства: «записать», «сказать о себе», «выждать»). Гейт не пускает вид дальше 5% корпуса и семейство дальше 9%, чтобы универсальный приём не стал советом на всё; список видов автоматически добавляется к промпту для модельных авторов.

Гейт (`scripts.gate_content`) работает без LLM. По тексту: ключи, поля и длины, обращение на «вы»,
о читателе — без рода и полных форм (морфология pymorphy3, `scripts/ru_gender.py`), запреты на
обещания, медицину и финансы; в текстах аспектов — без сравнения с другими аспектами той же пары, и нигде — без отсылок к знаку и дому, которых в тексте нет. По корпусу (`scripts/corpus_checks.py`, `--context` — уже принятое):
шаблонные начала полей и их предложений, форма «ярлык: …», избитые обороты (> 6% корпуса и > 12%
текстов одного вида), переклички между текстами, повторы внутри текста, занятые заголовки.
Бриф подсказывает и соседей по отчёту (тексты, которые всегда стоят рядом: рецепция и знаки,
достоинство и знак), реально встречающиеся варианты и годы рождения — всё из выборки карт.

Пространство контента считается из доктрины точно: 1271 ключ
(`sign:VENUS:AQUARIUS`, `aspect:SUN:CONJ:MERCURY`, `ruler:2:in:12`, `rule:...`).
Отчёт показывает заголовки фактов и честно перечисляет, где текста ещё нет.

## Что дальше

1. **Обучение весов.** W и V сейчас — априор. Когда в сети появятся исходы
   (взаимный интерес, длина переписки), U = q·x — это билинейная модель; её веса
   подбираются логистической регрессией на парах. Заодно это честная проверка:
   если астрологические признаки не несут сигнала, обученные веса это покажут.
2. `halfvec` (pgvector ≥ 0.7) — вдвое меньше места; сейчас ~100 КБ на профиль.
3. Фильтры знакомств (пол/кого ищу, возраст, страна) — до ANN, в SQL.
4. Транзиты и «окна» — тот же аппарат: транзитная карта как ещё один x.
